# loop 운영 규약 (loop-guide)

> 구현을 무인 사이클로 굴리는 범용 규약. 실증 사이클에서 증류했다.
> **루프는 하나다** — 작업이 크든 작든 같은 구조를 쓰고, 스펙·feature·사이클의 분량만 비례한다.
> 모든 프로젝트 loop가 이 문서를 읽는다. 프로젝트 고유분(함정·검증 인프라)은 각
> `docs/projects/<slug>/progress.md` 상단 절이 얹는다. 상태 파일 스키마는 `docs/loop/state-files.md`.

## 0. 출처와 전제

- 방법론 원천: Addy Osmani, "Loop Engineering" (https://addyo.substack.com/p/loop-engineering) —
  6요소·3대 경고·"작성자≠채점자". 루프 분류(단일/플릿/오픈/클로즈드)는 2차 자료
  (discuss.pytorch.kr/t/loop-engineering/10796)의 정리다. 이론 전문은 원문으로 —
  이 문서는 운영 규약만 담는다.
- **이 워크스페이스는 클로즈드 루프다**: 사람이 목표·완료 기준·정지점을 설계한다. features.json의
  `verify`가 단계별 기계 판정 기준이고, 전 feature 판정 완료(`passes: true` ∨ `blocked`)가
  **유일한 정지 판정**이다. 외부 개념 `/goal`(별도 모델의 완료 판정)은 이 환경에 없다 —
  Claude Code 내장 `/loop`(주기 재실행)만 가용하고, 턴 상한은 `blocked` 서킷브레이커(§4-5)가 담당한다.
- 대응 원리: **상태는 파일에, 판단은 Advisor에, 노동은 Worker에.** 이 세 분리가 루프 신뢰의 기반이고,
  검증자 신뢰가 "손을 뗄 수 있는 유일한 이유"(Osmani)다 — Advisor 검증(§7)이 시스템의 척추.
- **§1은 결번이다(§0 다음이 §2). 재번호 금지** — 이 문서의 §번호를 문서 밖(AGENTS.md·스킬·
  서브에이전트·스크립트·상태 파일)에서 참조하므로, 번호를 당기면 그 참조들이 전부 어긋난다.

## 2. 무엇이 loop를 성공시키는가 (성공 요인)

1. **상태는 파일에, 판단은 Advisor에, 노동은 Worker에** — 세 분리가 전부의 기반.
2. **완료 기준(features.json)의 `verify` 필드가 검증 절차 그 자체가 된다** — desc보다 verify를 공들여 써라.
3. **검증은 재실행이 아니라 실구동** — 테스트 통과 ≠ 동작. 실행·관찰이 각각 다른 부류의 결함을 잡는다(§5).
4. **함정 목록은 복리로 쌓인다** — 사이클 N의 발견을 N+1 브리프에 넣으면 Worker 품질이 즉시 오른다(§9).
5. **판정의 근거는 항상 실측이다 (앵커 원칙)** — `passes`·감사·리뷰의 근거는 실행 관찰(verify 재실행·
   실구동·git 히스토리)뿐이다. 상태 파일·보고서끼리의 교차 대조는 판정 근거가 아니다 — 서류가 서류를
   확인하는 감사는 모든 숫자가 맞아떨어지면서 아무것도 검증하지 않는다.

## 3. 시작 전 체크리스트 (계획 단계)

- [ ] 스펙 문서 확정 — 물어볼 수 있는 건 전부 사전 질문으로 소진(AskUserQuestion 라운드).
- [ ] **사용자만 풀 수 있는 blocker 목록을 만들어 미리 비운다** (외부 자원 선점·크리덴셜·인프라 등).
- [ ] "문서에 없는 건 재량 + progress.md 결정 기록" 원칙을 스펙에 명문화.
- [ ] features.json 작성 — 검증 가능한 `verify` 필수, JSON 형식(모델이 함부로 안 고침), `passes`·`blocked`·`verified_at_commit`은 Advisor 전용.
- [ ] progress.md 뼈대 — 상단 고정 절(함정 목록·검증 인프라)에 환경 실측과 예상 함정을 심는다.
- [ ] **환경 사전 점검**: 툴체인 버전(버전 확인부터), 외부 자원 선점 여부, 권한(sudo 유무), E2E 도구 가용성.
- [ ] 리스크 예측을 progress.md(함정 목록·사이클 0 항목)에 기록해두고 종료 후 적중 평가한다(§10) — 회고의 질이 올라간다.

## 4. 사이클 루틴 (순서 고정)

1. **방향 잡기**: `git log --oneline -15` + progress.md 최근 "다음 할 일" + features.json의 미판정 목록(`passes: false`이고 `blocked` 없음).
   **이어서 선행 감사**: `passes: true`인 각 feature에 대해 `git log --oneline <verified_at_commit>..HEAD -- <대상 경로>`로
   판정 이후 대상 파일 변경을 확인한다(대상 경로 = desc에 명시된 산출물 경로 — 겹침 판단은 Advisor 재량).
   변경이 있으면 `passes`를 `false`로 강등하고 `verified_at_commit`을 지워
   재검증 대상으로 되돌린다(§11-1의 기계화 — 근거는 git 히스토리 실측이지 상태 파일끼리의 대조가 아니다).
2. **스모크**: `git status`(이전 사이클 잔류물 확인) + 프로젝트 스모크 검사. 깨져 있으면 복구 먼저.
3. **태스크 선택**: 의존관계상 가능한 미판정 feature(`blocked`는 건너뛴다). 상호 의존이면 1 Worker에 묶고, 독립이면 병렬(§6).
4. **Worker 위임**: Agent 도구로 §5 브리프. model은 프로젝트 지정 — 모델 규약은 `docs/harness-guide.md`.
5. **Advisor 검증(§7)** — 여기가 품질의 병목이자 핵심. Worker 보고를 믿지 말고 직접 diff·실구동.
   **서킷브레이커**: 같은 feature가 3사이클 연속 검증 실패면 재위임을 멈추고 features.json에 `blocked`(사유)로
   격상한 뒤 나머지 feature를 계속 돈다 — 무한 재시도로 예산을 태우지 않는다. 격상 시 사유에 두 접두사 중
   하나를 붙인다: `resolvable:`(에이전트가 원리상 풀 수 있으나 3사이클 소진) 또는 `human_blocked:`(크리덴셜·외부
   승인·수동 단계 등 사람만 풀 수 있음). `human_blocked:`는 3사이클을 기다리지 말고 사람만 풀 수 있음이
   확인되는 즉시 격상한다.
6. **fresh-context 리뷰**: 커밋 전 이번 사이클 diff를 리뷰 서브에이전트(기본: `reviewer`) 또는 `/code-review`에 맡긴다 —
   Advisor는 브리프 작성자이자 채점자라 자기 브리프의 맹점을 못 본다. 지적의 반영 여부는 Advisor가 판단한다.
   리뷰 브리프에는 판정 두 개를 함께 요구한다: ① diff가 스펙을 충족하는가 ② **이번 feature의 verify가
   이 diff를 채점하기에 충분한가**(스텁·편법으로도 통과할 수 있는 verify인지). ②가 불충분이면 `passes` 전에
   verify를 강화하고 재검증한다(강화는 Advisor 재량, 완화는 §12 경로).
7. **기록**: 통과분만 커밋(**push 금지 — 사람 몫**) + features.json `passes`/`blocked` 갱신 + progress.md 사이클
   항목 — 소절: 한 일 / 결정(재량 결정은 코드 1줄이라도) / 토큰(소비 요약 한 줄) / **다음 할 일**.
   순서는 2단이다: **통과분 코드를 먼저 커밋**하고, 그 해시를 `verified_at_commit`에 적어 상태 파일
   (features.json·progress.md)을 갱신한 뒤 **상태 파일은 별도 커밋**한다(state-files §3).
8. **턴 종료 전**: progress.md "다음 할 일" → wakeup 예약. 전 feature 판정 완료(passes ∨ blocked) 시:
   마감 전 핵심 표면에 red-team 검증(깨뜨리기 시도)을 한 차례 수행하고(§7), 재사용 가치 있는 검증
   절차(E2E 스크립트·우회법)의 스킬 증류를 검토하고, wakeup 없이 **최종 보고**로 종료. 커밋·progress
   갱신은 보고가 아니다 — 최종 수신자는 사람이며, 보고에 다음 5종을 반드시 담는다:
   ① 판정 요약(passes/blocked 개수) ② 사이클별 핵심 산출·커밋 해시 ③ 주요 결정·발견 함정
   ④ 토큰 소비 ⑤ **남은 사람 몫**(push·draft 승격 등 — progress.md "다음 할 일"의 사람 몫 그대로).
   ⑤의 각 항목은 나열이 아니라 아래 **결정 브리프** 절의 형식으로 쓴다.
   blocked 목록에서 `human_blocked:` 건은 사용자가 풀기 위해 해야 할 액션을 함께 명시한다.
   무인 세션이라 보고를 전달할 수 없었다면 다음 대화 세션이 loop 마감을 인지한 즉시 같은 형식으로 보고한다.

### 결정 브리프 — 남은 사람 몫의 형식

- **원칙: 안전한 자율 단계를 소진하기 전에는 사용자에게 결정을 넘기지 않는다.** 묻기 전에 에이전트가
  할 수 있는 되돌릴 수 있는 안전한 단계(구현·검증·리뷰·초안 준비)를 전부 끝내고, 그러고도 남는
  정확히 그 결정만 올린다. 준비 안 된 결정 요청(막연한 "검토 필요", URL·상태 라벨 나열)은 금지.
- 남은 사람 몫의 각 항목은 아래 4필드를 채운 브리프 한 덩어리로 제시한다.

```
[결정] <사람이 내려야 할 결정 한 줄>
- 무엇이 바뀌나: 이 결정으로 무엇이 바뀌고 누가 이득인지 평문으로.
- 완료된 증거: 에이전트가 이미 끝낸 것 — 구현·검증·리뷰 상태. 사람이 재조사하지 않아도 되게.
- 선택지: 가능한 선택 각각과 그 결과(아무것도 하지 않는 경우 포함).
- 추천: 에이전트의 추천 하나와 그 근거. 판단을 사람에게 떠넘기지 않는다.
```

> 출처: 오픈소스 메인테이너들의 에이전트 오케스트레이션 관행 — 사람에게 올라오는 항목은 이미
> "결정 준비 완료" 상태여야 한다는 원칙에서 가져왔다.

## 5. Worker 브리프 템플릿 (고정 섹션)

```
[작업] F0XX: <무엇을>
[역할] 너는 Worker(구현자)다. 보고는 구현자 입장으로.        ← 역할 혼동 방지
[컨텍스트] 파일 경로, 재사용할 기존 모듈(재구현 금지 명시), 컨벤션
[검증 인프라] Advisor가 구축한 도구·경로·실행법            ← 고정 섹션(progress.md에 적어도 Worker는 안 읽음)
[스펙 요점] 해당 부분 발췌 — Worker가 재탐색하지 않도록
[함정] 누적 함정 목록에서 해당되는 것 전부(§8)
[산출물의 후속 용도] 나중에 어디 재사용되는지               ← 재사용 가능한 설계를 유도
[완료 기준] verify 필드 + "직접 실행해 결과를 보고에 포함하라". 보고는 4필드로 한다 — changed_files(변경·생성한 파일 목록) / decisions(재량 결정과 근거) / verification(실행한 명령과 그 출력 원문) / blockers(막힌 지점·미해결 사항, 없으면 '없음')
[금지] 상태 파일·docs 수정, git commit/push, .env 읽기, (병렬 시) 다른 Worker 영역
```

## 6. 병렬화 규칙

- 조건: 파일 영역이 겹치지 않을 때만. 브리프에 (1) 영역을 파일 수준으로 명시 (2) 서로의 존재를 고지.
- Advisor는 영역별로 선별 커밋(`git add` 경로 지정).
- 한계: 병렬은 위임 시간만 겹친다 — **Advisor 검증은 순차라 병목은 그대로.** 사이클당 Worker 2개를 상한으로.
- Worker 병렬보다 먼저 유용한 것: "Worker 구현 + Advisor 인프라 준비"의 병렬.

## 7. 검증 사다리 (부류별로 잡는 결함이 다르다)

| 단계 | 잡는 결함의 부류 |
|---|---|
| 테스트 재실행(2~3회) | flaky 테스트 — Worker 실행 때만 우연히 통과 |
| 스펙 교차 대조 | 브리프에 없던 스펙 위반 |
| 실구동(curl 등) | 스텁·에러 형식·보안 실패 경로. 실패 경로는 Advisor가 하나 이상 추가 |
| red-team(깨뜨리기 시도) | 해피패스 검증이 못 잡는 것 — 오용 입력·경계값·인접 실패 경로·계약 위반 |
| 스크린샷(라이트/다크/모바일) | 자동화 게이트를 다 통과한 시각 결함 |
| 브라우저 E2E | 기술적으로 옳지만 UX가 틀린 것 |
| 프로덕션 E2E | 지연이 있어야만 재현되는 레이스 — 로컬에서 원리적으로 못 잡음 |

- 검증 실패 시 첫 질문: **"구현 탓인가 검증 탓인가."** 실증상 검증 실패의 절반이 검증 스크립트·환경 문제였다.
- 디버깅 사다리: 우회 경로 비교 → 최소 재현 → 관찰 지점 이동. 각 단계가 가설 공간을 절반으로 줄인다.
- 실험마다 "변경이 실제 반영됐는가"부터 확인한다(빌드 캐시에 속지 마라).

> 사례: playwright 셋업이 sudo 없는 환경에서 사이클 하나 분량의 우회를 요구했다. `window.confirm`
> 기본 거부(dialog 핸들러 필요), 하이드레이션 레이스(networkidle + POST 응답 대기)로 검증 자체가 결함원이었다.

## 8. 재위임 vs 직접 수정

- 검증 실패 → 같은 Worker에 SendMessage 재위임(컨텍스트가 살아 있어 빠름).
- 직접 수정 허용: 한두 줄 + **판단 무게가 가벼울 때.** 판단이 얽히면 코드가 1줄이어도 progress.md 결정 소절에 기록.
- 탐색적 디버깅(가설이 빠르게 바뀜)은 위임 부적합 — Advisor 직접.
- 비밀 취급(크리덴셜 생성·토큰)은 위임하지 않는다.

## 9. 누적 함정 목록 (범용)

- **환경**: 툴체인 부재, 외부 자원 선점, sudo 없음(→ 사용자 우회 다운로드), headless 브라우저 폰트 부재.
- **셸**: `pkill -f "패턴"`이 자기 명령줄과 매치(→ `"[p]attern"` 브래킷), 백그라운드 서버 포트 충돌(띄운 것 목록 관리).
- **gitignore**: unanchored 패턴이 소스 디렉터리를 조용히 무시(→ 루트 앵커 `/dir/`).
- **훅에 막힌 커밋**: pre-commit에 막힌 커밋의 변경은 조용히 워킹트리에 잔류 — 사이클 시작 시 `git status`.
- 프로젝트 고유 함정은 각 progress.md 상단 함정 목록에 누적한다.

> 사례: next.js standalone은 public/static을 수동 COPY해야 하고, `router.push`가 액션 revalidate 재조회와
> 경합했다(지연 환경에서만 재현 → 전체 내비게이션으로 회피). Edge 런타임에 bcrypt/DB 금지도 밟았다.

## 10. 측정치·리스크 예측 (캘리브레이션)

- 사이클 크기 스윗스팟: feature 5~10개. 13개가 상한선(검증 실패와 무관치 않았다).
- 후반으로 갈수록 검증:위임 시간비가 역전한다 — **Advisor 검증이 시스템의 병목.**
  개선: E2E 스크립트 뼈대는 Worker에게 만들게 하고 Advisor는 실행+판정만.
- **토큰 소비를 사이클 항목에 기록한다**(§4-7) — 스윗스팟·모델 선택 같은 캘리브레이션 주장에 숫자 근거가 생긴다.
- 대비 구조(커밋 + 상태 파일)는 무비용이다 — 단일 세션에 완주해도 유지 가치가 있다.
- **리스크 예측 적중 평가**: 계획 단계 예측을 종료 후 적중/빗나감으로 채점하고, 적중한 함정은 §3 체크리스트로 승격한다.

## 11. 3대 경고 (루프가 좋아질수록 날카로워진다)

1. **검증 부담은 사람 몫** — "'done'은 주장이지 증명이 아니다"(Osmani). `passes: true`는 Advisor가 직접 관찰한 뒤에만 찍는다. `passes: true` 이후 해당 feature의 스펙이나 대상 파일이 변경되면 그 passes는 재검토 대상이다 — verify를 재실행하기 전까지 신뢰하지 않는다(변경 감지는 §4-1 선행 감사가 `verified_at_commit`으로 기계화한다).
2. **comprehension debt(이해 부채)** — 루프가 빠를수록 존재하는 코드와 이해의 격차가 가속한다. progress.md의 결정 기록·위키로 이해를 따라잡게 한다.
3. **cognitive surrender(인지적 항복)** — 판단을 피하려고 루프를 쓰면 역효과("같은 행동, 반대 결과"). 루프는 판단을 대신하는 게 아니라 실어 나른다.

## 12. 기준 관리 — 스펙·verify가 틀렸을 때

루프는 자기 기준이 옳은지 스스로 물을 수 없다 — 기준 수정은 관리되는 별도 경로로만 한다.
사이클 중 스펙 결함이 드러나면 세 갈래로 처리한다:

1. **공백** (문서에 없는 것): 재량으로 정하고 progress.md 결정 소절에 기록 — 기존 원칙 그대로.
2. **완료 정의가 안 바뀌는 결함** (죽은 명령 경로·오타·§7에서 드러난 느슨한 verify): Advisor가 고치고
   progress.md 결정 소절에 기록. 단 verify는 **강화만** 재량이다(state-files §2).
3. **완료 정의가 바뀌는 수정** (목표·제약 변경, verify 완화, feature 추가·삭제): 해당 feature를
   `human_blocked: 스펙 결함 — <요지>`로 즉시 격상하고 §4의 결정 브리프 형식으로 사람에게 올린다.
   나머지 feature는 계속 돈다. 빠른 루프(사이클)가 자기 기준을 완화하기 시작하면 굿하트가 열린다 —
   **기준의 완화는 더 느린 루프(사람)의 몫이다.**
