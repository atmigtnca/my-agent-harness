# 하네스 운영 상세 (harness-guide)

> AGENTS.md 요약 절들의 원본. Advisor/Worker 위임 규약, 공용과 개인의 경계, 온보딩,
> 거버넌스(운영 모드)를 여기서 정의한다. AGENTS.md 요약과 다르면 이 문서가 이긴다.
> loop 절차의 원본은 `docs/loop/`, 스킬·서브에이전트 작성 규약은 `docs/agents-guide.md`.

## 모델 역할 분담: Advisor / Worker

메인 세션은 Advisor다. 판단에 집중하고, 구현 노동은 Worker(서브에이전트)에게 위임하라.

**모델 지정 원칙**: Worker는 Advisor보다 한 티어 아래 최신 모델을 쓴다. 구체 모델은 프로젝트가 정한다.

Advisor(메인 세션)가 직접 하는 일:

- 요구사항 분석, 작업 분해, 설계 결정
- Worker에게 줄 작업 브리프 작성
- 결과 검증: diff 직접 확인, 테스트·실구동 직접 실행
- 최종 커밋 승인, 사용자 보고

Worker(서브에이전트)에게 위임하는 일:

- 코드 작성·수정, 테스트 작성 등 구현 노동 전부
- Agent 도구로 위임하고 model은 위 지정 원칙을 따른다
- 서로 독립적인 작업은 병렬로 위임한다. 파일 영역이 겹칠 수 있으면 `isolation: "worktree"`로
  격리하고 Advisor가 worktree별 diff를 검증·통합한다. 같은 파일을 여럿이 고쳐야 하면 순차가 답이다

브리프 기준 (템플릿 원본: `docs/loop/loop-guide.md` §5):

- 네가 이미 파악한 컨텍스트를 담아 Worker가 재탐색하지 않게 하라
- 파일 경로, 프로젝트 컨벤션, 알려진 함정, 완료 기준(통과해야 할 검증)을 포함하라

실행과 검증의 분리:

- 구현은 Worker가, 검증은 Advisor가 한다 — 같은 주체가 만들고 승인하는 일은 없어야 한다.
- Worker는 마치면 변경 파일 목록·핵심 변경 요약·실행한 검증 결과를 보고한다.
- Advisor는 보고를 받은 뒤 반드시 자신의 도구로 diff를 열고 검증을 재실행해 확인한다.
  통과한 변경만 커밋 대상으로 승인한다 — Worker는 커밋하지 않는다.

경계:

- Worker의 완료 보고를 그대로 믿지 마라. diff와 검증으로 직접 확인한 뒤 승인하라.
- 검증 실패는 수정 브리프로 재위임하라. 직접 수정은 한두 줄의 사소한 마무리에만 허용된다.
- 커밋 전 fresh-context 리뷰의 기본 도구는 `reviewer` 서브에이전트다 — 구현 과정을 모르는
  별도 컨텍스트로 diff·스펙 충족을 검증한다(Advisor 자신이 브리프 작성자이자 채점자라 못 보는 맹점을 잡는다).
- 새 서브에이전트(`.claude/agents/*.md`)를 만들 때는 `docs/agents-guide.md` 규약을 따른다 —
  본문 골격 6절, `tools:` allowlist 필수, 판정형은 verdict enum, 구현형은 보고 4필드.

Worker 감독 규율:

- **진행 중인 Worker에 개입하지 마라.** 일관된 계획으로 굴러가고 있으면 끝까지 지켜본다 —
  조급한 중간 개입은 Worker의 컨텍스트를 오염시키고 하던 일을 흐트러뜨릴 뿐이다.
- **개입은 증거 기반 조건 4종에서만**: ① Worker가 블로커를 보고했을 때 ② 맡은 작업이
  소진돼 다음 지시가 필요할 때(완료 보고 뒤의 수정 재위임 포함 — loop-guide §8) ③ 반복 실패가 관찰되고 줄 교정이 구체적일 때
  ④ 위임한 과제에서 명백한 이탈이 관찰될 때. 넷 다 근거는 관찰된 증거다 — 불안은 아니다.
- **위임 후 기준을 올리지 마라.** 브리프의 완료 기준·검증 기준은 위임 시점에 고정이다.
  새 요구가 생기면 이번 위임을 그대로 마치고 다음 브리프에 담는다.

## 공용과 개인

커밋되는 모든 것은 이 repo를 쓰는 전원의 세션에 로드된다. 판단 기준 한 문장:
"전원의 세션에 있어야 하는가?" (개인 모드에서는 "미래의 내 세션에 있어야 하는가") —
아니면 개인 영역에 둔다.

| 자산 | 공용 (커밋됨) | 개인 (커밋 안 됨) |
|---|---|---|
| Claude 설정·훅 | `.claude/settings.json` | `.claude/settings.local.json` |
| Claude 스킬 | `.claude/skills/<이름>/` | `.claude/skills/my-<이름>/` |
| Claude 서브에이전트 | `.claude/agents/<이름>.md` | `.claude/agents/my-<이름>.md` |
| `.agents` 스킬 래퍼 | `.agents/skills/<이름>/` | `.agents/skills/my-<이름>/` |

개인 경계는 위치가 아니라 **`my-` 접두사**다 — .gitignore가 커밋을 막는다.
따라서 공용 자산에 `my-` 접두사 이름은 금지다. 개인 자산이 팀에 쓸모 있어지면
접두사를 떼고 커밋해 공용으로 승격한다. **위키에 개인 영역은 없다** — 위키는 정의상 공용이다.
개인 모드에서도 이 경계는 유지한다: "확신 없는 실험"은 my-, "굳은 것"은 공용 —
경계의 의미가 타인/나에서 실험/확정으로 바뀔 뿐이다.

## 온보딩 (최초 1회)

1. 이 repo 루트에서 `claude`를 실행하고 trust 다이얼로그를 수락한다 —
   **수락 전까지 공유 권한 설정과 훅이 전부 비활성**이다.
   AGENTS.md 규약을 읽는 다른 런타임을 쓴다면 `.agents/skills/`의 래퍼가 `.claude/` 정본을
   가리키므로, 그 런타임에서도 같은 절차·규칙이 그대로 적용된다.
2. `scripts/setup.sh` — 나머지 기계 검사·설정 전부를 한 명령으로: githooks 활성화
   (위키 형식 검사·비밀 검출 pre-commit), gitleaks·PyYAML 존재 확인,
   `git config user.name` 검사(위키 승인 기록 `verified_by`가 이 이름을 쓴다).
   경고가 나오면 안내를 따라 해결하고 다시 실행 — 전부 ✓면 끝.
3. 위키가 시공 전이면(repo 최초 1회) claude 안에서 `/wiki-start` — 상황을 인터뷰해
   운영 모드·섹션·태그·프로젝트 규약을 설계·시공한다.

모드 공통 — 어느 모드든 다음은 코어다(시공이 손대지 않는다):

- 신뢰 게이트: 승인 없이 `verified` 없음. draft→verified 라이프사이클은 SCHEMA가 정의한다.
- 규칙의 원본 우위: 위키↔코드 불일치 시 코드가, AGENTS.md↔원본 문서 불일치 시 원본이 이긴다.

### 팀 모드

- **위키 책임자(DRI): <이름>** — 이 repo의 설정·문서 컨벤션·위키 품질을 최종 책임진다.
  분기마다 위키 큐레이션(잔여 draft·만료·고아 문서 처분)을 수행한다.
- **위키 검증은 분산되어 있다**: 세션 중 기록을 승인한 사용자가 그 문서의 검증자다(`verified_by`).
  책임자는 개별 문서의 검증자가 아니라 위키 전체의 품질 관리자다.
- 규칙 개정 제안은 자유 — 결정은 책임자가 한다.

### 개인 모드

- **책임자 = 사용자 본인.** DRI·검증자·승인자가 전부 한 사람이어도 게이트는 유지한다 —
  "세션 중 확인"(절차는 SCHEMA "기록 경로")의 목적은 타인 검토가 아니라
  **노이즈 필터와 의식적 검토**이므로 혼자여도 생략하지 않는다.
- 분기 큐레이션(`/wiki-curate`)도 본인 몫이다 — 큐레이션 때 `scripts/wiki-stale-check.py`를
  실행해 재검토 대상을 잡는다(자동 알림은 없다 — 주기는 스스로 지킨다).
- 팀 전제 문구("팀원 전원", "온보딩")는 "미래의 나", "새 머신 셋업"으로 읽는다.
  나중에 팀이 되면 위 "운영 모드" 줄을 팀으로 바꾸고 DRI를 기입한다 — 모드 절은
  둘 다 정본으로 남아 있으므로 지우거나 복원할 것이 없다.
