# 위키 스키마

이 위키는 **팀과 AI 에이전트가 공유하는 세션 간 지식 저장소**다.
이 문서는 위키의 구조·형식·라이프사이클을 정의하며, 여기 없는 규칙은 규칙이 아니다.

## 대원칙

1. **위키는 원본의 지도이지 대체물이 아니다.** 모든 지식 문서는 `sources`로 원본(코드·PR·문서)을 가리킨다. 위키 내용과 원본이 다르면 **원본이 이긴다.**
2. **쓰는 건 마찰 없이, 믿는 건 게이트 뒤에.** 누구든(에이전트 포함) draft(초안)를 리뷰 없이 커밋할 수 있다. 신뢰는 **사람의 승인**을 거친 verified(검증됨)만 갖는다 — 승인자는 그 맥락을 아는 세션 사용자(즉시) 또는 위키 책임자(DRI, 큐레이션)다.
3. **필터 없는 축적 금지.** 기록의 경로는 세션 중 확인 하나뿐이며, 아래 "기록 트리거"를 통과한 것만 기록한다. 트리거 없는 기록은 노이즈다.
4. **비밀은 위치만 가리킨다.** 크리덴셜 값은 절대 기록하지 않는다.

## 단일 프로젝트 — 위키 하나가 repo 하나를 기억한다

이 위키는 **이 repo가 담당하는 하나의 프로젝트**의 기억이다. 그래서 **귀속 표시가 없다** —
어느 프로젝트 것인지 적는 칸(frontmatter 필드·경로 규칙·색인 그룹핑)을 두지 않는다. 섹션이
가르는 것은 "어느 프로젝트냐"가 아니라 "어느 방에서 찾을 지식이냐"뿐이다.

**프로젝트가 여럿이면 위키가 아니라 repo를 늘린다.** 이 하네스는 템플릿이다 — 새 프로젝트는
템플릿을 한 벌 더 찍어 거기서 `/wiki-start`로 시공한다. 한 위키에 여럿을 밀어 넣으면 방이
프로젝트 이름으로 채워져 3±1 원칙이 깨지고, 조회 트리거의 `grep`이 남의 문서에 적중하며,
문서 예산("크기 상한" 절)이 프로젝트 수만큼 곱해진다. 한 프로젝트 안의 갈래(컴포넌트·서비스·과목)는
브라우징으로 찾을 것이면 방으로, 검색으로 찾을 것이면 태그로 가른다. 이 전제는 코어다 —
시공이 바꾸는 것은 방·태그·규약이지 위키의 개수가 아니다.

## 디렉토리 구조 — 뼈대와 시공

```
wiki/
├── SCHEMA.md          # 이 파일 — 불변 코어 규칙 + 이 위키의 설정·규약
├── index.md           # 색인 — 기계 생성 (wiki-lint), 손으로 편집 금지
└── <섹션>/            # 시공 시 결정 — frontmatter config.sections가 원본
```

섹션(방) 구성은 템플릿이 정하지 않는다 — 최초 1회 `/wiki-start` 시공이 상황을
인터뷰해 설계하고, `config.sections`와 아래 "프로젝트 규약" 절에 기록한다.
섹션이 비어 있는 동안 위키는 **시공 전** 상태다: 문서를 기록할 수 없다 (wiki-lint가 막는다).

**루트에는 `meta`만, `meta`는 루트에만** (wiki-lint 강제). 루트에 놓을 수 있는 것은 `type: meta`
— 이 SCHEMA·index, 그리고 시공이 원하면 개요 한 편 — 뿐이고 나머지는 전부 섹션 안이다. 섹션 안의
`meta`는 색인에 실리지 않아 아무도 열지 않는 사각지대라 거부한다(방 소개·목차는 색인이 이미 한다).
섹션에 안 속하는 전체 개요의 자리는 둘뿐이다: 매 세션 읽히는 `AGENTS.md`, 또는 루트 meta 개요
한 편(색인 머리에 링크가 실린다). 지식(왜·구조·함정)은 개요가 아니라 섹션 안 knowledge다.

섹션 설계 원칙 (시공·재시공 공통):

- **방은 적게 시작한다 (3±1).** 빈 방은 부채다 — 한 방에 문서가 10개를 넘어 섞이기 시작할 때 쪼개는 것이 순서다.
- **브라우징으로 찾는 지식만 방을 갖는다.** 검색(grep)으로 찾는 지식(사고 사례, 문제풀이 기록)은 방을 쪼개지 않고 `tags`로 구분한다.
- **섹션과 문서 유형(type)은 독립이다.** 어떤 섹션에든 어떤 유형이든 놓일 수 있다 — 방은 발견의 구조, 유형은 신뢰의 구조다.
- **섹션 이름 = 디렉토리 이름.** `wiki/` 바로 아래 한 조각 — 슬래시·공백·빈 값·점 시작·중복 불가
  (wiki-lint가 `config.sections`를 이 규칙으로 검사한다). 소문자 한 단어를 권한다.

**좋은 방의 검산 — 셋 다 통과해야 방이다**: **착지**(6개월 뒤 던질 질문이 5초 안에 이 방에 착지하는가
— 안 떠오르면 방이 아니다) · **배타**(새 문서를 놓을 방이 하나로 정해지는가 — 둘이 동시에 맞으면
경계가 틀렸다) · **인구**(6개월 안에 3편이 차는가 — 안 차면 방이 아니라 태그다).
**안티패턴**: 배타 없는 하수구(`misc`·`기타`·`temp`) / 프로젝트·서비스 이름의 방("단일 프로젝트" 절)
/ 그 유형만 놓이도록 강제하는 유형의 사본(`troubleshooting/`이라는 방 자체는 괜찮다) / 시간·상태의
방(`2026`·`archive`·`wip` — `updated`·`status`가 가진 것을 디렉토리로 복제하면 둘이 어긋난다) /
깊은 중첩(`wiki/a/b/c/` — 색인은 최상위 방만 그룹으로 본다).

## 색인 — 훑기의 입구이자 운영 신호판

`index.md`는 wiki-lint가 frontmatter에서 재생성한다(손으로 편집 금지). 목록이자 **건강 상태판**이다 —
훑으러 온 사람이 그 자리에서 큐레이션 대상을 보게 하는 것이 목적이다. 머리에 전체 집계(문서 수·검증됨·
초안·만료, ~50 초과면 경고)와 루트 meta 개요 링크(어느 방에도 없어 훑기에서 빠지는 것을 막는다)를,
방마다 같은 집계 한 줄을 싣는다
(빈 방은 `(비어 있음)`으로 남아 "빈 방은 부채"를 스스로 신고한다). 문서 한 줄은 제목·경로·상태 라벨·
`summary`(색인의 본문 — 훑는 사람은 제목이 아니라 이 줄을 읽고 열지 말지 정한다), 만료면 `⚠️ 만료`.
정렬은 방 순서가 `config.sections` 그대로(설계자가 정한 우선순위), 방 안은 **신뢰 순 → 제목 순**
(검증됨·채택됨 → 초안·제안됨 → 대체됨) — 바닥에 몰린 초안 덩어리가 그대로 큐레이션 대기열로 보여야
하기 때문이다. 색인은 상태의 **표시**이지 게이트가 아니다 — 처분은 사람이 한다("유지보수" 절).

## 프로젝트 규약 — 시공이 채운다

> ⚠️ 아직 시공 전이다. 최초 1회 `/wiki-start`가 인터뷰를 거쳐 이 절과 frontmatter
> `config`를 채운다. 시공 전에는 문서를 기록할 수 없다.

이 절은 시공 후 다음을 정의한다 — 코어 규칙과 충돌할 수 없다 (충돌하면 코어가 이긴다):

- **섹션**: 각 방의 목적 한 줄과 배치 기준 ("이 지식은 어느 방인가"의 판단 규칙)
- **태그**: 각 태그의 의미와 부여 기준 (또는 "태그 자율" 선언)
- **원본(sources) 규약**: 이 위키가 지도로 삼는 원본이 무엇인가(코드·인프라 구성·문헌·실험 기록 등) —
  sources에 무엇을 적는 것이 유효한지가 여기서 정해진다.
- **트리거 구체화**: 코어의 기록·조회 트리거가 이 프로젝트에서 어떤 모습인지 예시 목록
- **연결 관례**: 문서 간 링크 규칙 — 연결이 중요한 위키(학습 등)는 "본문 끝 `## 관련` 절에 관련 문서
  링크"처럼 명시한다 (고아 문서는 audit이 잡는다)

**변경 이력의 장부는 git이다.** 수기 이력 파일은 두지 않는다 — 조회는 `git log --oneline -- wiki/`.
위키를 변경하는 커밋은 **제목 한 줄이 곧 장부의 한 줄**이며, 형식은 하나로 고정한다:

```
wiki: <동작> — <대상>: <요지>
```

- **동작** (6개 고정): `기록` | `승격` | `수정` | `삭제` | `큐레이션` | `시공`
- **대상**: 파일명(확장자 생략 가능). 여러 개면 쉼표, 위키 전반이면 `*`
- **요지**: 무엇이 왜 — 승인이 있었으면 `(승인: <이름>)`을 끝에

```
wiki: 기록 — adr-001-cache-strategy: 캐시 계층을 Redis 단일로 결정 (승인: 홍길동)
wiki: 승격 — build-pipeline: sources 대조 일치 (승인: 홍길동)
wiki: 삭제 — redis-cache-tips: 캐시 개편으로 전제가 사라짐        ← 삭제 기록 ("삭제" 절)
wiki: 큐레이션 — *: 분기 훑기, draft 3건 승격·1건 삭제 (승인: 홍길동)
wiki: 시공 — *: 학습 위키로 신축 — 섹션 3개·연결 관례 정의 (승인: 홍길동)
```

제목만 보고 "무엇이 왜"를 알 수 있어야 한다 — 상세는 커밋 본문에.
commit-msg 훅이 이 형식을 강제한다 (index.md 재생성만 있는 커밋은 예외).

## 문서 유형과 frontmatter

모든 문서는 frontmatter로 시작하며 `type`은 다음 5가지 중 하나다:

| type | 용도 | status 허용값 | 유효기한 기본 | sources |
|---|---|---|---|---|
| `knowledge` | 아키텍처·도메인·운영 지식 | `draft`(초안) → `verified`(검증됨) | 6개월 | 필수 |
| `troubleshooting` | 증상→원인→해결 사례 | `draft`(초안) → `verified`(검증됨) | 12개월 | 필수 |
| `decision` | 결정 기록(ADR) | `proposed`(제안됨) → `accepted`(채택됨) → `superseded`(대체됨) | 없음 | 필수 |
| `redirect` | 이동/통합된 문서의 포인터 | 없음 | 없음 | 대상 경로 |
| `meta` | SCHEMA, index | 없음 | 없음 | — |

### 공통 frontmatter

```yaml
---
type: knowledge
title: 빌드 파이프라인 구조
summary: 빌드 3단계 구조와 새 타깃 추가 시 확장 지점   # index.md에 실리는 발견용 한 줄 — 필수
status: draft                # type별 허용값만
updated: 2026-07-05          # 내용을 실제로 고친 날짜
review_by: 2027-01-05        # 유효기한 — updated + type별 기본값. 지나면 "만료" 취급
verified_by: 홍길동           # verified/accepted 문서만 — 승인한 사람. draft에는 없음
sources:                     # 원본 포인터 — 코드 경로, PR, 문서, 대화 요지
  - src/build/
  - "PR #142"
tags: [infra]                # config.tags가 정의된 프로젝트만 필수 (허용 목록에서 선택)
---
```

### 유형별 본문 형식

- **knowledge**: 자유 형식. 단 첫 문단은 "이 문서가 답하는 질문"이 드러나야 한다.
- **troubleshooting**: `## 증상` → `## 원인` → `## 해결` → `## 재발 방지` 4개 섹션 고정. frontmatter에 `symptoms:` 필수 — 에러 메시지 원문·증상 키워드 목록. 미래 세션의 grep이 적중하는 지점이므로 표현을 다듬지 말고 **원문 그대로** 적는다.
- **decision**: `## 맥락` → `## 결정` → `## 근거(대안 포함)` → `## 결과` 형식. 파일명 `adr-NNN-<슬러그>.md`, 번호는 이어서 증가. 결정을 뒤집을 때는 기존 문서를 고치지 않고 새 결정 기록을 쓰고 옛것을 `superseded`로 바꾼다.
- **redirect**: 본문 한 줄 — `→ [새 위치](경로)로 이동 (YYYY-MM-DD, 사유)`.

## 기록 경로 — 세션 중 확인

기록의 경로는 이것 하나다. 자동 수거 백스톱은 없으므로 **세션이 끝나기 전에 기록하지 않으면
그 지식은 사라진다** — 세션 말 회고(`/wiki-record`)가 마지막 기회다.

에이전트는 작업 중 기록 트리거에 해당하는 지식이 생기면 메모해 두었다가 **진행 중인 작업이 마무리된 시점에** 모아서 기록을 제안한다 — 작업 흐름을 끊지 않는다(세션이 끝나기 전이기만 하면 된다):

1. 문서를 SCHEMA 스펙대로 작성하되 커밋 전에 **본문 전체를 사용자에게 보여주고** 기록 여부를 묻는다.
   (요약만 보여주고 승인받는 것 금지 — 안 읽은 승인은 게이트가 아니다.) 본문 끝에는 **요약(변경 요지·핵심
   주장 몇 줄)을 덧붙인다** — 긴 문서의 승인 판단을 돕는 부록이지 본문의 대체가 아니다. 재승인(수정 후
   승격 포함) 때도 같다. 승인 요청에는 `git config user.name`에서 읽은 이름으로 **"<이름> 이름으로
   기록합니다"를 명시**한다 — 이름이 비어 있거나 누구인지 알아볼 수 없으면(기본값·공용 계정 등) 그때만
   직접 묻는다. 실명일 필요는 없지만(팀이 알아보는 핸들이면 충분) **추론으로 채우는 것은 금지** —
   잘못된 verified_by는 검증 체계 전체를 오염시킨다.
2. 사용자가 승인하면 `status: verified`(decision은 `accepted`) + `verified_by: <사용자>`로 커밋한다.
   그 순간의 세션 사용자가 해당 지식의 맥락을 가장 잘 아는 검증자다.
3. 사용자가 거절하면 기록하지 않는다. 수정을 요구하면 반영 후 다시 확인받는다.

**자율 세션 예외**: 사용자가 실시간 응답할 수 없는 세션(goal/loop, headless, cron, 백그라운드)에서는 묻지 않는다 — 세션이 끝나기 전에 직접 `draft`로 기록한다(수거해줄 백스톱이 없다). **사용자 승인 없이 verified는 불가능하다.**

## 조회 트리거 — 쓰기 전에 읽는다

기록 트리거와 대칭이다. 다음 상황에서는 코드 탐색을 계속하기 전에 위키를 먼저 검색한다
(`grep -ri "<증상·키워드>" wiki/`, 훑기는 `index.md`):

1. **같은 에러·증상에 2회 이상 막힘** — 과거 troubleshooting이 있을 확률이 가장 높은 지점
2. **절차·구성·소재가 필요할 때** (배포 절차, 크리덴셜 소재, 환경 구성) — 해당 섹션 먼저
3. **"왜 이렇게 되어 있지?"** — 구조·설정에 의문이 들면 decision 문서 먼저

조회 없이 삽질 30분을 채우고 기록 트리거 ①로 오는 것은 실패 경로다 — 위키의 존재 이유가 그 30분을 없애는 것이다.

## 기록 트리거 — 이 5가지일 때만 쓴다

1. **삽질 30분 이상** — 다음 사람(또는 다음 세션의 에이전트)이 같은 시간을 쓰지 않도록
2. **같은 질문이 2번째 나옴** — 사람이든 에이전트든
3. **운영 사고/장애** — troubleshooting으로
4. **되돌리기 어려운 구조적 결정** (아키텍처·인프라·방법론) — decision으로
5. **AGENTS.md 심화** — AGENTS.md가 한 절로 감당하지 못하는 주제를 옮겨 심을 때. AGENTS.md에는
   요약 한 줄 + 위키 링크만 남기고 심화 본문을 knowledge로 쓴다. 경계 둘: 코드에서 곧장 재도출되는
   **열거형 정보(라우터 목록·테이블 수 따위)는 위키에도 쓰지 않고**(가장 빨리 썩고 가치가 가장 낮다 —
   재도출 비용이 큰 "왜·구조·함정"만 옮긴다), repo 안 상세 가이드(중첩 CLAUDE.md, `docs/`)와
   **중복하지 않는다**(가리키기만 — 코드에 갇힌 상세는 코드 곁에). 이 트리거는 조회 입구가
   grep이 아니라 AGENTS.md의 링크다 (AGENTS.md에서 링크되지 않으면 그 심화 문서는 진입로가 없다 —
   "유지보수" 절의 고아 문서가 된다).

**기록 전 검산 — "이 repo를 겪지 않은 유능한 에이전트도 이미 아는 지식인가?"** 그렇다면
트리거를 통과했더라도 기록하지 않는다. 위키에 남는 것은 이 프로젝트의 특수 경험 —
왜 여기서는 일반 해법이 안 통했나, 무엇에 걸려 넘어졌나, 왜 이렇게 결정했나 — 뿐이다.
일반 지식(언어·도구·프레임워크의 표준 동작)은 모델이 이미 갖고 있고 세션마다 갱신되므로
기록하는 순간부터 문서 예산("크기 상한" 절)만 잠식하는 노이즈다. 삽질 끝의 해결책이 알고 보니 일반
지식이었다면 해결책 자체가 아니라 **이 프로젝트에서 그것이 문제가 된 이유**만 남긴다.

작성 전 의무: `grep -ri "<키워드>" wiki/`로 기존 문서 확인. 있으면 새 문서 대신 그 문서를 고친다.

## 라이프사이클

### draft → verified (knowledge, troubleshooting)

verified가 되는 경로는 두 가지뿐이다. 어느 쪽이든 **사람의 승인**이 게이트다:

1. **세션 중 사용자 승인** (기본) — 위 "기록 경로" 절차. 본문을 읽고 승인한 사용자가 `verified_by`에 남는다.
   기존 draft(자율 세션 산출물 등)도 세션에서 실제로 사용·검증하게 됐다면 본문을 보여주고 승인받아 승격할 수 있다.
2. **책임자 큐레이션** (분기) — 승격되지 않고 남은 잔여 draft를 책임자가 훑는다
   (`grep -rl "status: draft" wiki/`가 승격 대기 목록). 페이지당 판정: ✅ verified 승격 /
   ✏️ 고쳐서 승격 / 🗑️ 삭제. 판정 사유는 커밋 메시지에.

- 에이전트는 **사용자 승인 없이 verified로 커밋할 수 없다** (자율 세션 포함, 예외 없음).
- **verified 문서를 수정하면 status를 draft로 되돌린다** (에이전트 포함, 예외 없음 — 오타 수정도).
  "검증된 문서 위에 얹힌 미검증 수정"이라는 상태는 존재할 수 없다. 단, 수정 직후 세션 사용자에게
  변경 본문을 보여주고 승인받으면 그 자리에서 다시 verified가 된다.

### 유효기한 (review_by)

- `review_by`가 지난 문서는 **만료** 상태다. 삭제되지 않지만 신뢰가 강등된다.
- **만료는 기계가 표시한다**: wiki-lint(pre-commit)가 만료 문서 본문 최상단에 `> ⚠️ 만료(review_by …
  경과)` 배너를 자동 삽입하고 `review_by` 갱신 시 제거한다. 손으로 넣거나 지우지 않는다 — grep·Read로
  문서를 연 에이전트가 frontmatter를 해석하지 않아도 만료를 놓치지 못하게 하는 장치다. 색인에도 표시된다.
- **에이전트 지침**: 만료 문서는 `sources`를 직접 확인한 후에만 근거로 사용하라.
  대조 결과 내용이 여전히 맞다면 사용자 승인 하에 `updated`/`review_by`를 갱신할 수 있다.
- 책임자는 분기 큐레이션에서 남은 만료 문서를 처리한다: 내용 확인 후 갱신 또는 삭제.

## 삭제 — 지울 수 있어야 좋은 위키다

- **사람은 자유롭게 삭제한다.** 단 커밋 메시지에 사유 필수: `wiki: 삭제 — <파일>: <사유>`. 이 커밋이
  **삭제 기록**이 되어 같은 오지식의 재기록을 막는다 (기록자는 작성 전 `git log --diff-filter=D -- wiki/`로 확인).
- **에이전트는 직접 삭제할 수 없다.** 고침으로 해결되지 않는 문서(주제 자체가 틀림·무가치)를 발견하면
  본문 최상단에 `> ⚠️ 부정확 의심: <사유>` 경고 삽입 + draft 강등까지만 — 경고가 삭제 확정 전까지의
  즉각 격리 장치다. 삭제 확정은 사람(세션 사용자 또는 책임자)이 한다.
- **redirect vs 삭제**: 이동·통합 = redirect / 틀림·무가치 = **완전 삭제** — 틀린 내용으로 가는 길을 남기지 않는다.
- 복구는 git 이력으로 한다 (`git log --follow`, `git checkout <해시> -- <파일>`).
  `decision`은 삭제하지 않고 `superseded`로 (역사는 지우지 않는다).
- 삭제로 깨진 내부 링크는 wiki-lint가 pre-commit에서 잡는다.

## 크기 상한

- 문서 300줄 이하. 넘으면 **분할보다 삭제·압축을 먼저** 검토한다. 이 예산은 지식 문서의 것이고
  **SCHEMA.md 자신은 예외다**(wiki-lint도 제외한다) — 코어 규칙 문서인데다, 시공이 채우는 규약
  분량을 상한이 막으면 첫 시공 커밋 자체가 불가능해진다. 다른 meta 문서에는 상한이 그대로 적용된다.
- 위키 전체 ~50문서 목표. 늘어나기만 하는 위키는 실패한 위키다. 이건 프로젝트 하나의 예산이라
  좁아지면 위키가 아니라 문서를 줄인다("단일 프로젝트" 절) — 색인 머리 집계가 총계와 초과 경고를 낸다.

## 유지보수

검증은 세션 사용자들이 상시 분산 수행하므로, 책임자의 정기 작업은 분기 큐레이션 하나다:

- **분기 (책임자)**: 잔여 draft 처분 + 만료 문서 처리 + **고아 문서**(= 자동 생성 색인
  `wiki/index.md`를 제외한 어떤 진입로(AGENTS.md·다른 위키 문서 본문)에서도 링크되지 않는 문서 —
  색인은 모든 문서를 자동으로 싣기 때문에 진입로로 세지 않는다. 이 정의가 원본이며 자동화·스킬은
  이 절을 참조한다)·모순·태그 정합성 점검 + 이벤트형 무효화 대조(`scripts/wiki-stale-check.py` — updated 이후 `sources`
  경로가 변경·소멸된 문서 목록) — 에이전트에게 점검을 시키되 처분은 책임자가 한다 (`/wiki-curate`).
  판정 사유는 커밋 메시지에 남긴다.
- **형식은 기계가**: frontmatter 검증, 300줄 초과, redirect 링크 유효성, 문서 위치(섹션 안·meta는 루트),
  `config.sections` 이름 규칙, index.md 재생성, 만료 배너 삽입·제거는 `wiki-lint`(pre-commit/CI) 담당 —
  책임자는 내용만 본다
