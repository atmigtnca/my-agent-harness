# wiki-start — 위키 시공

> **발동 선언**: 이 스킬을 실행할 때 "wiki-start 프로토콜 발동합니다"라고 선언하고, 실행 중·보고에서도 같은 명칭을 쓴다.

이 템플릿은 **뼈대(코어)** 와 **시공 영역**으로 나뉜다. 코어는 지속 가능성의 장치들 —
신뢰 게이트(draft→verified), 원본 우위(sources), 시간 방어(만료·stale-check), 노이즈 필터
(트리거·상한), 삭제 규칙, 자동화(lint·훅), 거버넌스 — 이고 **어떤 상황에서도 손대지 않는다.**
너의 일은 나머지, 상황의 함수인 부분을 채우는 것이다:

| 시공 영역 | 어디에 쓰나 |
|---|---|
| 섹션(방) 구성 | `wiki/SCHEMA.md` frontmatter `config.sections` + 디렉토리 생성 |
| 태그 체계 | `config.tags` (또는 빈 목록 = 태그 자율) |
| 프로젝트 규약 | SCHEMA의 "프로젝트 규약" 절 — 섹션 목적, 태그 의미, sources 규약, 트리거 구체화, 연결 관례 |
| 프로젝트 소개 | `AGENTS.md` 첫 문단 |
| 운영 모드·거버넌스 | `docs/harness-guide.md` "거버넌스" 절 — "운영 모드" 줄 확정(개인/팀), 팀이면 책임자 기입 |

규칙의 원본은 `wiki/SCHEMA.md`다 — 특히 "디렉토리 구조 — 뼈대와 시공" 절의 섹션 설계
원칙과 "프로젝트 규약" 절의 정의 목록. 충돌하면 SCHEMA가 이긴다.

## 0. 상태 확인

`wiki/SCHEMA.md` frontmatter의 `config.sections`를 본다:

- **비어 있음 → 신축.** 아래 절차 그대로.
- **차 있음 → 재시공.** 기존 문서가 한 편이라도 있으면 아래 "재시공" 절의 이전 계획이
  추가로 필요하다. 이유 없이 재시공을 권하지 마라 — 방 배치가 불편하다는 것이 확인된
  뒤에 고치는 것이 순서다.

## 1. 인터뷰 — 상황을 파악한다

프리셋을 들이밀지 마라. 사용자의 상황은 네가 아는 어떤 예시와도 다를 수 있다 —
아래 네 가지를 알아낼 때까지 대화한다 (한 번에 다 묻지 말고, 답에서 다음 질문을 끌어내라):

1. **원본이 무엇인가** — 이 위키가 지도로 삼는 대상. 코드? 인프라 구성? 문헌·강의?
   실험? 원본이 무엇이냐에 따라 `sources` 규약이 달라진다 (코드 경로 / 서버·설정 소재 /
   문헌 서지·URL / 실험 로그).
2. **지식이 어떤 형태로 생기나** — 절차(runbook)? 사고·삽질의 해결? 개념·이론?
   결정? 문제풀이? 형태가 섹션과 유형 매핑을 정한다.
3. **미래의 질문 3개** — "6개월 뒤 이 위키에 와서 무엇을 찾고 싶은가"를 구체적 질문으로
   받아라 (예: "그때 OpenStack 네트워크를 왜 그렇게 구성했지?"). **섹션은 이 질문들이
   5초 안에 착지할 곳으로 역설계한다** — 이것이 설계의 검산식이다.
4. **누가 쓰나 — 운영 모드를 확정한다.** 혼자면 **개인 모드**, 여럿이면 **팀 모드**
   (모드별 거버넌스 규약은 `docs/harness-guide.md` "거버넌스"가 정의한다 — 개인 모드도
   승인 게이트는 유지된다는 점을 사용자에게 알려라). 팀이면 위키 책임자(DRI)가 누구인가.
   "곧 팀이 될 예정"이면 현재 인원 기준으로 정한다 — 재시공 경로가 있으니 미리 팀 모드로
   짓지 않는다.

## 2. 설계

**설계의 검산식은 인터뷰 3번의 "미래의 질문 3개"다.** 프리셋이나 남의 위키 구조에서
출발하지 말고, 그 질문 하나하나가 5초 안에 착지할 곳을 역설계해 방을 만든다. 후보 설계가
나오면 세 질문을 다시 굴려 착지 지점을 확인하고, 어떤 질문도 받지 못하는 방은 짓지 않는다.

그 위에 SCHEMA의 섹션 설계 원칙(방은 3±1로 적게 / 브라우징 지식만 방을, 검색 지식은
태그로 / 섹션과 유형은 독립)을 적용한다. 추가로:

- **문서 유형은 만들지 않는다.** 5유형(knowledge·troubleshooting·decision·redirect·meta)은
  코어다. 상황에 따라 어떤 유형을 주로 쓸지가 달라질 뿐이다 (학습 위키라면 decision이
  드물고, 인프라 위키라면 troubleshooting이 주력).
- **트리거는 없애지 말고 구체화한다.** 코어의 기록 트리거 5종을 이 상황의 언어로 번역한
  예시 목록을 규약에 적는다 (트리거 ①이라면 "디버깅 30분+"·"배포 삽질 30분+"처럼
  사용자가 자기 일로 알아볼 문장으로).
- **연결이 중요한 위키**(학습처럼 지식이 그물일 때)는 연결 관례를 규약에 명시한다:
  본문 끝 `## 관련` 절에 관련 문서 링크 + 왜 관련인지 한 구절. 고아 문서는 audit이 잡는다.

## 3. 승인

설계안 전체를 표로 제시한다: 운영 모드(개인/팀 + 그 모드에서 거버넌스가 어떻게 작동하는지
한 줄) / 섹션(각각 목적 한 줄 + 배치 기준) / 태그(각각 의미) /
sources 규약 / 트리거 구체화 / 연결 관례 / 책임자. **"미래의 질문 3개"가 어느 방에
착지하는지 답과 함께 보여라** — 사용자가 설계를 검산할 수 있는 유일한 방법이다.
승인 전에는 아무것도 쓰지 않는다. 수정 요구는 반영 후 다시 보여준다.

## 4. 시공 — 승인 후

1. `wiki/SCHEMA.md` frontmatter `config`의 `sections`·`tags` 갱신.
2. SCHEMA "프로젝트 규약" 절의 placeholder 인용문을 지우고 설계 내용으로 채운다
   (섹션·태그·sources 규약·트리거 구체화·연결 관례 — 그 절이 정의한 목록 그대로).
3. 섹션 디렉토리 생성 + 각각 `.gitkeep`.
4. `AGENTS.md` 갱신: 첫 문단을 프로젝트 소개로 교체.
5. `docs/harness-guide.md` "거버넌스" 갱신: "운영 모드" 줄을 확정 모드로 채우고,
   팀 모드면 책임자(DRI) 이름을 기입한다. **모드 절 두 개와 모드 공통(신뢰 게이트·
   원본 우위)은 규약 정본이므로 지우지 않는다** — 활성 규약은 "운영 모드" 줄이 가리킨다.
6. `python3 scripts/wiki-lint.py` 실행 — 통과 + index.md 재생성 확인.
7. 커밋 (SCHEMA 장부 형식): `wiki: 시공 — *: <상황 요약> — 섹션 N개 (승인: <이름>)`.
   이름은 `git config user.name`에서 읽고 "<이름> 이름으로 기록합니다"를 승인 때 명시한다.
8. **첫 이사 제안 (선택)**: 사용자가 이미 가진 지식·문서가 있으면 1~2건을 SCHEMA 스펙으로
   옮겨 기록 경로(본문 승인 → verified)로 남기기를 제안한다 — 빈 위키보다 실물 예시
   한 편이 규약을 잘 가르친다. 거절하면 그대로 끝낸다.

## 재시공 (기존 문서가 있을 때)

1. 현 문서 전수 목록 → 새 섹션 매핑표를 만들어 설계안과 함께 승인받는다.
2. 이동은 `git mv`로 (이력 보존). 외부에서 경로가 참조될 만한 문서만 redirect를 남긴다 —
   SCHEMA "삭제" 절의 redirect 규칙 준용.
3. lint 실행으로 깨진 내부 링크를 잡고 전부 고친 뒤 커밋:
   `wiki: 시공 — *: 재시공 — <요지>, 문서 N편 이동 (승인: <이름>)`.

## 금지

- 코어 수정 ❌ — 문서 유형·라이프사이클·승인 게이트·훅·자동화 스크립트는 시공 대상이 아니다.
  코어가 상황과 안 맞는다고 판단되면 고치지 말고 사용자에게 한계로 보고하라.
- 인터뷰 없이 시공 ❌ / 승인 없이 시공 ❌
- 섹션 6개 이상 설계 ❌ — 정말 필요하면 사용자에게 "빈 방은 부채" 원칙과 함께 근거를 제시하고
  명시적 동의를 받아라.
- 위키를 여러 개로 쪼개기 ❌ — **repo 하나에 위키 하나**다. 분리가 필요하면 방(섹션)이나
  태그로 나누고, 그래도 안 되면 사용자에게 한계로 보고하라.
- 시공 커밋에 wiki/·AGENTS.md·docs/harness-guide.md 밖의 파일 섞기 ❌
