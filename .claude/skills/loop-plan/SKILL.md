# loop-plan — loop 프로젝트 시공

> **발동 선언**: 이 스킬을 실행할 때 "loop-plan 프로토콜 발동합니다"라고 선언하고, 실행 중·보고에서도 같은 명칭을 쓴다.

Claude Code 내장 `/loop`(주기 재실행 기능 — 이 repo의 스킬이 아니다)로 굴릴 새 프로젝트의
**파일 3개**(스펙 SSOT + 상태 2종)를 시공하는 스킬이다. **루프는 하나다** —
작업이 크든 작든 같은 구조를 시공하고, 분량만 비례한다. 규격의 원본은 두 문서다 —
손대지 말고 그대로 따르라:

- **`docs/loop/state-files.md`** — 각 파일의 필수 헤딩·형식(§5)과 features.json 스키마(§3), verify 3요건(§4).
  **이 스킬이 만드는 모든 파일 구조는 여기서 온다. 충돌하면 state-files가 이긴다.**
- **`docs/loop/loop-guide.md`** — 인터뷰 항목의 원천(§3 시작 전 체크리스트)과 사이클 루틴(§4).

시공하는 것은 **상태 파일의 뼈대 + 확정된 스펙**뿐이다. 사이클 루틴·브리프 템플릿·검증 사다리는
loop-guide에 이미 있으니 복제하지 말고 progress.md 상단에서 참조로 가리킨다.

## 0. 모드 판정 — 인터뷰인가 무인인가

- **사용자가 실시간 응답 가능 → 인터뷰 모드.** §1~§4 전부.
- **사용자 부재(loop 세션·headless) → 무인 모드.** §1의 인터뷰(AskUserQuestion)를 생략하고 §2를 건너뛴다.
  주어진 스펙 텍스트만으로 시공하되 **미확정 사항은 전부 progress.md 사이클 0 항목의 결정 소절에
  '재량' 표기로 남긴다**(임의로 덮지 말고 판단 근거를 적는다). §3~§5는 두 모드 공통이다.

slug를 먼저 정한다: 소문자 영문·숫자·하이픈만, 동사+대상 또는 대상 한 단어(예: `docs-site`).
디렉토리명이 곧 slug이고 상태 파일·커밋이 이 이름을 참조하므로 **시공 후 변경 금지**(state-files §0).

## 1. 인터뷰 — 스펙을 확정한다 (loop-guide §3)

AskUserQuestion 라운드로 아래 5개 항목을 소진한다. 한 번에 다 묻지 말고 답에서 다음 질문을 끌어내라.
**인터뷰 종료 판정은 질문 수가 아니라 항목 소진이다** — 5개 항목이 각각 **확정**(사용자 답변) /
**재량**(근거 명시) / **해당 없음**(근거 명시) 중 하나가 될 때까지 라운드를 계속한다. "이 정도면 명확하다"는 에이전트의 추정은 종료
사유가 아니다. 질문 수는 불확실성에 비례하므로 정말 명확한 소형 작업이면 짧게 끝나는 게 맞지만,
그 판정은 아래 모호성 검출을 통과했을 때만 성립한다. blocker 소진(2)은 크기 무관 불변 —
**"없음"도 사용자의 명시적 답변으로만 확정된다.**

1. **스펙 확정** — 무엇을 만드는가. 목표·제약·완료 정의를 물어볼 수 있는 건 전부 지금 소진한다.
   "문서에 없는 건 재량 + progress.md 결정 기록" 원칙을 스펙에 명문화할 것임을 알린다.
2. **사용자만 풀 수 있는 blocker 목록** — 외부 자원 선점·크리덴셜·인프라 접근·계정 등, loop가 무인으로는
   못 푸는 것. **이 목록을 만들어 발사 전에 비운다.** 이것이 이 스킬의 최우선 산출이다.
3. **환경 사전 점검** — 툴체인 버전(버전 확인부터), 외부 자원 선점 여부, 권한(sudo 유무), E2E 도구 가용성.
   실측해 progress.md "검증 인프라" 절에 기록한다. **실측은 실행한 명령과 그 출력 원문**(버전 문자열 등)을
   그 절에 남겨야 성립한다 — 명령·출력 원문 없는 "확인됨"·"가능" 기록은 실측이 아니라 추정이므로 무효다.
4. **리스크 예측** — 어디서 막힐지 계획 단계 예측을 progress.md 함정 목록·사이클 0 항목에 남긴다
   (종료 후 적중 평가 — loop-guide §10).
5. **발사 명령 문안** — 내장 `/loop`에 줄 프롬프트 한 줄을 확정한다(실증상 최대 구멍이 발사 명령 미정의였다).

### 모호성 검출 — 하나라도 걸리면 그 지점은 "명확"이 아니다. 반드시 물어라

1. **판정 기준 없는 추상 표현** — "깔끔하게", "적당히", "잘 되게", "안정적으로", "예쁘게".
   이대로는 verify를 못 쓴다. 무엇이 관찰되면 만족인지로 바꿔 확정한다.
2. **완료 정의 부재** — 무엇이 보이면/통과하면 끝인지가 사용자 언어로 확정되지 않았다.
3. **범위 경계 부재** — 이번에 **안 하는 것**(out of scope)이 한 줄도 없다.
4. **구현 대상의 실체 공백** — 화면·엔드포인트·데이터 형식·입출력 예시 중 무엇도 구체화되지 않았다.
   ("관리자 페이지 만들어줘" — 어떤 항목을 보여주고 어떤 조작이 가능한가?)
5. **기존 것과의 관계 미정** — 신규인가 수정인가, 어느 코드·페이지·테이블에 붙는가.
6. **동작에 영향 주는 수량·조건 미정** — 몇 건까지, 누가 쓰는가, 실패 시 어떻게 되는가.

묻는 방식: 열린 질문("어떻게 할까요?") 대신 **구체안 2~3개를 역제안**하고 고르게 한다
(AskUserQuestion 옵션으로). 사용자가 "알아서 해줘"라고 답하면 그 지점은 **재량으로 확정**하고
requirements.md에 재량 범위를 명문화한다 — 추정으로 조용히 채우는 것과 재량 선언은 다르다.

feature 분해 지침: 사이클 크기 스윗스팟은 feature 5~10개(13이 상한). phase로 실행 순서·병렬 가능성을
나눈다(같은 phase라도 파일 영역이 겹치면 병렬 불가 — loop-guide §6).

## 2. 승인 — 인터뷰 모드에서만

features 목록(각 id·phase·desc·verify)과 완료 정의, blocker 목록을 표로 제시해 승인받는다.
**특히 각 feature의 verify를 함께 보여라** — 완료 판정 기준이 맞는지는 사용자만 검산할 수 있다.
승인 전에는 아무 파일도 쓰지 않는다. 수정 요구는 반영 후 다시 보여준다.

**소진 게이트 (필수)**: 승인 표에 인터뷰 항목 5개 각각의 상태를 명시한다 —
**확정**(어느 답변으로 확정됐는지) / **재량**(왜 안 물었는지 + 재량 범위) / **해당 없음**(근거).
이 표 없이 승인을 청하지 않는다. 안 물은 항목은 여기서 그대로 드러나야 하며, 사용자가 표를 보고
"이건 왜 재량이야?", "왜 해당 없음이야?"라고 잡아낼 수 있는 것이 이 게이트의 목적이다 —
재량·해당 없음의 근거도 사용자 검산 대상이다.

## 3. 시공 — `docs/projects/<slug>/`에 3개 파일

`requirements.md`·`features.json`·`progress.md`를 **state-files §3(features.json 스키마)과
§5(파일별 필수 구조) 규격 그대로** 시공한다 — 헤딩·필드·최상단 규약을 여기 옮겨 적지 않는다(복제 금지).
시공 전에 그 두 절을 열어 따르고, 만든 구조가 규격에 맞는지는 `scripts/loop-lint.py`가 대신 본다.
시공의 마지막으로 progress.md 첫 항목 `## 사이클 0 — <날짜> — 시공`을 만들고 **다음 할 일**
(첫 wakeup이 할 일 = blocker 소진 확인 후 사이클 1)로 끝낸다 — 이 항목의 결정 소절이 §0 무인 재량의 기록처다.

## 4. verify 작성 — desc보다 verify를 공들여라 (state-files §4)

각 feature의 verify는 **state-files §4의 3요건** — 기계 판정 가능 · 실행 명령 포함 · 성공 판정값
명시 — 를 모두 만족해야 한다. 하나라도 빠지면 그 feature는 미완성이다. 요건의 정의·좋은 예·
나쁜 예는 state-files §4가 원본이다 — 여기 옮겨 적지 않는다(복제 금지). 시공 전에 그 절을 열어
그대로 따르라.

## 5. 시공 직후 자기 검사 (필수 — 두 모드 공통)

시공한 파일을 스스로 검사한 뒤 보고한다. 실패하면 고치고 재실행한다. **무인 모드에서도 아래 전 단계를
그대로 실행한다** — 기계 검사·리뷰·실측 기록 요구는 사용자 부재와 무관하다.

1. **기계 검사** — `python3 scripts/loop-lint.py`가 통과해야 한다(상태 파일의 JSON 형식·필수 필드·헤딩
   구조 검사를 이 lint가 대신한다 — 여기서 중복 나열하지 않는다). lint는 verify의 문구 표면도 휴리스틱으로
   본다 — 추상어 잔존·실행 명령 부재·판정값 부재는 이제 기계가 잡아 주므로 손으로 재확인하지 마라. 대신
   자기 확인은 lint가 못 보는 **의미 충족**에 쓴다: 명령과 판정값이 박혀 있어도 그 verify가 desc의 완료를
   실제로 증명하는가(이 자기 확인과 다음 리뷰가 함께 본다). **progress.md "검증 인프라" 절에 §1.3 실측의 명령과 출력 원문이 실제로 적혀 있는지
   확인한다** — 명령·출력 원문 없는 "확인됨" 기록은 실측이 아니므로 여기서 걸러낸다. 또한 lint가 못 보는
   세 가지를 직접 확인한다: state-files §5의 **최상단 1줄 규약**이 3파일 각각에 있는지, features.json에 `blocked`
   필드가 **시공 시점에 존재하지 않는지**, `passes`가 **전부 false인지**(뒤 둘은 사이클 중에는 합법인
   생애주기 규칙이라 lint가 강제할 수 없다).
2. **reviewer fresh-context 리뷰 (발사 게이트)** — 시공한 3파일(requirements.md·features.json·progress.md)을
   `reviewer` 서브에이전트에 위임해 **의미 적합성**을 판정받는다. 문구 표면은 lint의 몫이고, 리뷰는 lint가
   못 보는 의미를 본다 — 이 구분을 브리프에 적어 넘긴다. **판정은 총점이 아니라 항목별이다**: 아래 고정
   항목 집합을 브리프에 그대로 싣고, 항목마다 `OKAY`/`ITERATE` + 사유를 표로 반환받는다. **점수·퍼센트를
   요구하지도 받지도 않는다.**

   고정 항목 집합 — 하나도 빼지 말고 전부 넘긴다:

   | 항목 | 판정 질문 |
   |---|---|
   | A1~A6 | §1 모호성 검출 6종 **각각**에 대해: 그 모호성이 requirements.md·features.json에 아직 남아 있는가 (A1 추상 표현 — lint 패턴 목록 밖 어휘와 `desc` 필드까지, 어휘 매치가 아니라 **판정 가능성** 기준으로 / A2 완료 정의 / A3 범위 경계 / A4 구현 대상의 실체 / A5 기존 것과의 관계 / A6 수량·조건) |
   | B (feature마다 한 항목) | 이 feature의 verify가 전부 통과해도 desc·목표가 미완성일 수 있는가 — verify는 desc의 완료를 **실제로 증명**하는가 |
   | C | 완료 정의·제약이 인터뷰 확정 사항(무인 모드면 주어진 스펙 텍스트)과 일치하는가 |

   reviewer의 output_contract는 그대로다 — **전체 verdict는 여전히 정확히 하나**(OKAY/ITERATE/REJECT)이고,
   항목별 판정표는 `## Findings`에 싣게 한다. **전 항목이 OKAY일 때만 전체 OKAY**임을 브리프에 못박는다.

   **게이트: 전 항목 OKAY.** ITERATE가 하나라도 있으면 반영한 뒤 재검하고, 재검은 **매 라운드 fresh
   reviewer**에게 전 항목을 처음부터 다시 받는다(직전 라운드의 통과를 물려받지 않는다). 수용하지 않는
   지적은 사유를 progress.md 사이클 0 항목의 결정 소절에 기록하고 그 상태로 재검을 청한다 — 수용 판단은
   Advisor의 몫이지만, 기록 없이 무시하는 것은 금지다.

   **계획 서킷브레이커** — 같은 항목이 **3라운드 연속 ITERATE**면 그 항목은 리뷰로 안 풀린다:
   - **인터뷰 모드**: 그 항목을 loop-guide §4 "결정 브리프" 형식(무엇이 바뀌나·완료된 증거·선택지·추천)으로
     사용자에게 격상해 **확정받은 뒤에만** 진행한다.
   - **무인 모드**: 발사를 포기한다. 미해소 항목과 사유를 progress.md 사이클 0 항목의 결정 소절에 기록하고
     사람 보고 대기 상태로 종료한다.

   **REJECT**(접근 자체 재고)는 라운드로 세지 않는다 — 반복 재검이 무의미한 판정이므로, 인터뷰 모드는
   즉시 결정 브리프로 사용자 격상, 무인 모드는 즉시 발사 포기다.

   **리뷰 통과 전 발사 금지** — 전 항목 OKAY를 받기 전에는 내장 `/loop`를 쏘지 않는다.
3. 인터뷰 모드면 마지막에 blocker 목록을 사용자에게 리마인드하고, 발사는 blocker 소진 후임을 알린다.

## 금지

- **상태 파일 스키마(state-files) 수정 ❌** — 필드·헤딩을 바꾸지 말고 그대로 시공한다. 스키마가 상황과
  안 맞으면 고치지 말고 보고하라.
- **인터뷰/승인 없이 인터뷰 모드 시공 ❌** — 무인 모드가 아니면 승인 전에 파일을 쓰지 않는다.
- **passes를 true로 시공 ❌** — 시공 시 전부 false. passes는 Advisor 전용(state-files §2).
- **리뷰 게이트를 총점·점수·임계점으로 대체 ❌** — 게이트는 항목별 verdict의 전 항목 OKAY다. 숫자 점수는
  채점 노이즈로 통과가 갈리고 자기 기준 완화(굿하트)를 연다(agents-guide §7).
