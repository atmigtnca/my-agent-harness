# 세션 밖 작업 인계

> **발동 선언**: 이 스킬을 실행할 때 "handoff 프로토콜 발동합니다"라고 선언하고,
> 실행 중·보고에서도 같은 명칭을 쓴다.

인계문은 **명령서가 아니라 시작 맥락**이다. 받는 쪽은 다른 시각·다른 체크아웃·다른 시점에서
일을 시작하므로, 여기 담긴 상태는 도착하는 순간 이미 낡았을 수 있다. 그 전제 위에서 쓴다.

## 1. 언제 쓰는가 — Worker 브리프와의 구분

| | Worker 브리프 (`docs/loop/loop-guide.md` §5) | handoff 인계문 (이 스킬) |
|---|---|---|
| 받는 쪽 | 같은 repo의 서브에이전트(필요 시 worktree로 격리) | 다른 세션·다른 머신·다른 사람의 에이전트 |
| 맥락 | 내가 파악한 경로·컨텍스트를 **최대한 이식** | 스냅샷이 낡을 수 있다고 보고 **앵커만** 이식 |
| 첫 지시 | 브리프대로 구현 | **독립 재검토** 후 스스로 판단 |

작업을 지금 이 세션에서 계속 굴릴 수 있으면 인계하지 마라 — 인계는 경계를 넘을 때만 이득이다.

## 2. 절차

### ① 인계 대상 식별

사용자가 짧은 라벨("그 로그인 버그", "리팩터링 건")만 줬다면 대화 이력, 현재 브랜치명,
언급된 이슈·PR에서 대상을 유추해 **한 줄로 되물어 확정**한다. 대상이 흐린 채로 쓰면
인계문 전체가 흐려진다.

### ② 맥락 수집

네 가지를 모은다. 확인되지 않는 칸은 비워두지 말고 "미확인"이라고 적는다.

- **트리거** — 무엇이 이 작업을 촉발했나(에러, 리뷰 코멘트, 사용자 요청, 실패한 테스트)
- **현재 상태** — 어디까지 했나, 어디서 멈췄나, 커밋됐나 아닌가
- **제약** — 건드리면 안 되는 것, 유지해야 할 동작, 마감·의존
- **알려진 증상** — 재현 방법과 정확한 에러 문구

### ③ 인계 프롬프트 작성

§3 규칙과 §4 골격을 따른다. 길이는 받는 쪽이 한 번에 읽을 분량으로 — 배경 설명을 늘리는 대신
받는 쪽이 직접 확인할 앵커를 정확히 준다.

### ④ 전달

클립보드 복사 도구를 쓸 수 있으면 복사하고 "복사했다"고 알린다. 없으면 `.handoff/` 아래에
파일로 저장하고 경로를 안내한다(이 디렉토리는 gitignore 대상 — 인계문에는 진행 중 작업의
내부 사실이 담기므로 커밋하지 않는다). 어느 쪽이든 **전달 수단을 사용자에게 명시**한다.

### ⑤ 화면 출력은 요청받을 때만

본문 전문은 사용자가 "보여줘"라고 할 때만 출력한다. 기본은 전달 완료 보고
(대상 작업 한 줄 + 전달 수단)까지다.

### 자율 세션이면

자율 세션(정의는 `wiki/SCHEMA.md` "자율 세션 예외")에서는 ①의 되묻기를 생략하고
브랜치·이슈·대화 이력에서 대상을 유추하되, 불확실한 항목은 골격의 `추정:` 줄에 모은다.
전달은 `.handoff/` 파일 저장으로 고정하고, 그 경로를 완료 보고(progress 기록 등)에 남긴다.

## 3. 인계 프롬프트 규칙

**받는 쪽의 독립 재검토가 첫 지시다.** 인계문의 첫 과제는 구현이 아니라 검증이다 —
repo와 문서, 최신 상태를 직접 확인하고 ⓐ 이 작업이 여전히 유효한지 ⓑ 이미 해결됐는지
ⓒ 더 작고 안전한 해법이 있는지를 스스로 판단하라고 명시한다. 인계문의 진단과 다른 결론이
나오면 **인계문이 아니라 받는 쪽의 확인이 이긴다**고 적는다.

**경로 대신 이식 가능한 앵커.** 절대경로·홈 디렉토리 경로·체크아웃 디렉토리 이름을 쓰지 않는다.
받는 쪽의 트리는 위치도 이름도 다르다. 대신 이렇게 가리킨다:

- repo 이름, 브랜치명, 이슈·PR URL
- 모듈·클래스·함수 등 심볼 이름
- 정확한 에러 문구, 로그 한 줄, grep으로 찾을 검색어
- repo 루트 기준 상대경로는 허용하되, 그 자체를 검색어로도 함께 준다

**안전 기본값을 인계문 자체에 적는다.** push, 머지, 이슈·PR 닫기, 공개 코멘트 작성,
파괴적 명령(강제 삭제·리셋·마이그레이션 실행)은 **인계문이 명시로 요구하지 않는 한 금지**라고
받는 쪽에게 직접 말한다. 인계는 권한 위임이 아니다.

**날조 금지.** 확인한 것만 사실로 적고, 나머지는 "추정:"으로 표시한다. 기억으로 쓴 파일명·함수명·
버전은 확인 전까지 추정이다. 그럴듯한 세부는 받는 쪽의 재검토를 오히려 망친다.

## 4. 인계 프롬프트 골격

```
# <작업 제목 — 한 줄>

## 맥락
- 트리거: <무엇이 이 작업을 부르게 했나>
- 현재 상태: <어디까지 됐나 / 어디서 멈췄나 / 커밋 여부>
- 제약: <유지할 동작·건드리지 말 것·기한>
- 알려진 증상: <재현 절차 + 정확한 에러 문구>
- 앵커: <repo·브랜치·이슈 URL·심볼명·검색어>
- 추정: <확인 못 한 항목을 여기에 모아 표시>

## 구현 전에 할 일 (첫 지시)
코드를 고치기 전에 위 앵커로 현재 상태를 직접 확인하라. 그리고 판단하라 —
이 작업이 아직 유효한가, 이미 해결됐는가, 더 작은 해법이 있는가.
위 맥락과 네 확인이 다르면 네 확인이 이긴다. 다르면 먼저 그 사실을 보고하라.

## 과제
- 할 것: <완료의 정의>
- 하지 않을 것: <범위 밖 — 곁다리 리팩터링·무관한 정리>

## 검증 기대
<통과해야 할 테스트·명령, 또는 없다면 어떻게 확인할지>

## 출력 형식
1. 재검토 소견 (유효/불필요/대안 — 근거와 함께)
2. 변경 요약과 변경 파일 목록
3. 실행한 검증과 그 결과

## 안전 기본값
push·머지·이슈 닫기·공개 코멘트·파괴적 명령은 이 인계문이 명시로 요구하지 않는 한 하지 않는다.
막히면 추측으로 밀지 말고 멈추고 질문하라.
```

## 금지

- 절대경로·홈 디렉토리 경로·로컬 체크아웃 이름을 인계문에 넣기 ❌
- 확인 안 한 파일명·에러·버전을 사실처럼 적기 ❌ (추정 표시 없이)
- 크리덴셜·토큰 값 삽입 ❌ (있는 위치의 이름만)
- "브리프대로 구현하라"로 시작해 재검토 지시를 빼먹기 ❌
